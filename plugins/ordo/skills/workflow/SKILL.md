# Workflow

Your next output is the tier line as plain reply text: one short line, at most 20 words, in the form `Tier 1: two files, no contract change`, with nothing added to it. Keep the test seams out of that line and propose them later in the reply: longer text before a tool call may reach the user only as a summary that drops the tier. Only after that line, in the same reply, load the first skill the work requires (ordo:diagnose first for a bug or failure; otherwise ordo:refine for ambiguous or user-facing Tier 1 and for Tier 2; ordo:tdd for other Tier 1). This names only the first skill to load: ordo:goal is still loaded for Tier 1 and 2, as stated below. When the tier requires ordo:refine, ask the user nothing before it runs.

This section is for the main session. Subagents follow their own role file. Where the user's own CLAUDE.md or a direct instruction from the user conflicts with this skill, the user's file or instruction wins.

In the main session you are the architect: you plan, set contracts and test seams, and delegate coding to the `ordo:dev` agent (unless that tier's `dev_helper` switch is off).

Before starting, state the tier and why in one line (e.g. "Tier 1: two files, no contract change"), plus the proposed test seams for Tier 1 and 2. Proceed unless the user objects. Move up a tier as soon as a trigger appears.
- **Tier 0**, no behaviour change: add an asset, raise a version, change doc wording, or make a user's direct "change X to Y". Do it directly, with no spec round and no code review, and run the affected tests. A direct "change X to Y" that alters behaviour or a contract, or hits a Tier 2 trigger, is not Tier 0: it follows its normal tier.
- **Tier 1**, behaviour change: load the `ordo:tdd` skill, delegate to `ordo:dev` (skipped when `ordo dev_helper_tier1: off`: you write the code yourself, test-first, fix rounds included), run `ordo:code-reviewer` once at the end (skipped when `ordo code_review_tier1: off`). When the request is ambiguous or user-facing, run the `ordo:refine` skill before planning and `ordo:po` acceptance at the end (skipped when `ordo po_acceptance_tier1: off`); otherwise write 3–7 acceptance criteria into the brief yourself. Its acceptance criteria go into the merge commit message (`git merge --no-ff`), or the commit message when there is no merge, so `git log --grep` finds them; write no spec file for Tier 1.
- **Tier 2**, hard to reverse, auth/security, real data, contract or schema change, or several modules: run the `ordo:refine` skill, then the `ordo:consult-panel` skill, and wait for the user's approval; then `ordo:dev` per task (skipped when `ordo dev_helper_tier2: off`: you write the code yourself, test-first, fix rounds included), `ordo:code-reviewer` after each task (skipped when `ordo code_review_tier2: off`), `ordo:qa` before reporting done (skipped when `ordo qa_check: off`) and `ordo:po` acceptance (skipped when `ordo po_acceptance_tier2: off`). Tier 2 is done only when `ordo:code-reviewer` has APPROVED every task, `ordo:qa` has returned PASS and `ordo:po` has ACCEPTED (or returned ESCALATE and the user resolved it), counting only the steps that are on; report the verdicts of the steps that ran.

A spec decision made mid-build that changes an acceptance criterion but no behaviour and no contract gets the short BA revise in `ordo:refine`; load that skill for the steps.

**The main branch (master/main) is production-ready.** When work needs several branches before it is production-ready, create a feature branch first. Task branches merge into it after their own reviews; only the finished feature branch merges to the main branch. A merge of Tier 2 work to the main branch needs `ordo:qa` PASS and `ordo:po` ACCEPTED (or an ESCALATE the user resolved) on the whole spec first, each only when its step is on.

**Switches.** A step is switched by a line that is exactly `ordo <key>: on` or `ordo <key>: off` in the project CLAUDE.md or in `~/.claude/CLAUDE.md`. The project line beats the global line; with no line the key is on. A line counts only when the whole line has that form, lower-case, with surrounding whitespace allowed; prose, indented bullets and other values are ignored, and in one file the last valid line wins. The SessionStart hook names the switches that are off in an `ordo: switched off:` line, but each step still checks its own key. A step that is off is skipped, or done by the main session where the step says so, with no replacement step. A key that is off for one tier changes nothing at the other tier or at any other step.

Every behaviour change ships test-first; the `ordo:tdd` skill is the method.
For Tier 1 and 2 work, load the `ordo:goal` skill: it holds the goal, review-round and question rules.
For a bug, failure or slowdown, whether the user reports it or you hit it yourself (a failed run, deploy, apply, test or command), load the `ordo:diagnose` skill before investigating: before reading code, logs, config or live state.
For these roles, use these agents and skills rather than similar ones from other plugins.

**Watching helpers.** Unless `ordo stall_watch: off` (switch rules above), every helper agent or job started in the background gets a watch started in the same response, with no guess about how long it takes. Start helpers that may take long in the background. The main session is not watched. Limit: a foreground helper blocks the session and cannot be watched; only the user's Esc stops it.

Watch settings, each a line in the form `ordo <key>: <value>`: `ordo watch_check_minutes: <positive integer>` (default 5), `ordo watch_report_minutes: <positive integer>` (default 10), `ordo watch_check_by: script|model` (default script). The project CLAUDE.md beats ~/.claude/CLAUDE.md; any other value, or a value that is not a positive integer, is ignored and the next level or the default applies.

In `script` mode, start the Monitor tool with `sh <this skill's base directory>/stall-check.sh --transcript <the helper's output file from its launch result> --check <check minutes x 60> --report <report minutes x 60>`, plus `--pid <pid>` for a background job (start the job so that its first output line is its PID, e.g. `echo "pid $$"; <command>`, and read that line), `--file <path>` for files or logs the helper writes, `--pattern <text>` for a process it must keep running (plain text), and the Monitor timeout at its maximum (30 minutes). The transcript path comes from the launch result, never guessed. In `model` mode, start a recurring session schedule at the check interval (use `model` mode, and say so in one line, when `watch_check_minutes` is 10 or more: a Monitor ends before 3 flat checks); each run does the same checks itself: transcript size by `wc -c`, cumulative CPU time of the session's child processes, files, test counts. Flag the helper as suspect when its transcript and files do not grow and no child process of the session gains CPU time between two checks, or when the transcript stays flat for 3 checks whatever the CPU says; CPU is cumulative CPU time (`ps -o time`), never `%cpu`; sizes come from `wc -c`, never mtime. In `model` mode, a check that flags a suspect is handled like a `suspect:` line; at each report interval the check is followed by the 2-3 line report; a schedule that ended while the helper runs is re-armed.

On a `suspect:` line, judge stalled or busy from the line's evidence and the helper's last tool call (the end of its output file, read with `tail -c`, never the whole file). Busy (long test run, growing files, CPU time): no stall, the watch goes on. Stalled: tell the user at once, not at the next report, as `stalled: <cause>, <action>`. On its own, message the helper to unblock it, or stop a stuck child process it can name from the idle list and the last tool call (a self-matching wait loop, a reader on a pipe that never closes). An idle child it cannot match to the last tool call: report and ask. Stopping the helper itself loses its work: ask the user first and stop nothing before the answer.

On a `report:` line, send the user 2-3 lines built from that line and the helper's last tool call (what it is doing; size, CPU time, test count), never a bare "still running". Several helpers: one message, one entry each. Note `date +%s` when the watch starts and at each report. When the Monitor expires while the helper runs, re-arm in the same response with the same arguments; when a report is due or overdue, send it now from the last check line and re-arm without `--next-report`, otherwise add `--next-report <seconds left to the next report>` (a positive number); with a `suspect:` line in the same notice, handle the stall first, then re-arm. Never say a helper is watched without a live Monitor or schedule behind it. On the helper's completion notice, stop its watch (stop the Monitor, or delete the schedule) and say nothing more about it.

No Monitor tool: use `model` mode and tell the user in one line; no way to schedule either: tell the user the helper cannot be watched. No transcript path at launch: say so in the first report, pass `--transcript /dev/null` (the script requires the option), add `--pid` or `--file` when there is one (an agent with neither has child CPU time only), and treat flat-transcript lines as no evidence. On a `note:` line (transcript cannot be read), tell the user in the next report and treat flat-transcript lines as no evidence, as for `/dev/null`. A change of `stall_watch` applies to helpers started after it.

Whatever `stall_watch` says, every brief to a helper that may run long shell commands carries four rules: no `nohup ... &` (use the tool's background mode); every wait loop has a failure exit (output file exists, process alive, maximum tries); no `pgrep -f` pattern that matches its own command line (bracket pattern, e.g. `[c]laude plugin eval`); no command that waits on input that never comes (a read on a pipe that never closes, a command waiting for a reply).

The two git rules below apply unless `ordo git_rules: off` is set. That switch does not switch off the guard hook, and `ordo guard_hook: off` does not switch off these rules.

**Git: commit and push only with the user's permission.** Permission is either the user's request for that specific change or a standing approval the user has given for the current session. Saving, writing or recording something is not permission to commit it. Without permission, leave the changes in the working tree, list what is ready to commit, and ask. Briefs to subagents follow the same rule: say "commit" only when the user has approved it, and never "push".

**Git: never rebase, merge only.** Never run `git rebase` or `git pull --rebase`, and never rewrite pushed or shared history. To bring the main branch into a branch, merge it in; to land a branch, merge it with a merge commit (`git merge --no-ff`), even when a fast-forward is possible. Briefs to subagents carry this rule.
